# How the Claude Code team does code review

**Core idea:** When agents write most of the code, "did a human read it?" stops being the right test. The Claude Code team layers automated checks and AI review, spends scarce human approvals according to the risk of each change, makes mistakes fast to undo, and judges the whole system by human time spent, with reverts and incidents as the guardrail.

## Durable guidance
- **Ask what could go wrong with each change and which check, automated or human, should catch it, instead of asking whether a human read the code.** The authors call "did a human read the code?" an imprecise proxy for that question. Review moved from a gate at the end to something that runs continuously, like spellcheck while you write: most changes have been reviewed and fixed by Claude at least once before a human is asked to look, which saves team attention for higher-level questions.
- **Aim for the least human review time that doesn't raise reverts or incidents, and track both.** The goal is that most PRs merge with at most one human in the loop, who can be the author. Human time includes the time spent fixing what bad code breaks, so cutting review time doesn't help if the time just shows up in those fixes. The team tracks human approvals per PR (median and 95th percentile), human comments and how long a PR waits on a person, with revert and incident rates as the guardrail.
- **Have the agent verify its work before anyone else looks.** Give Claude something it can run (tests, a build, a screenshot to compare against the design) and ask it to show the output instead of saying it's done, then have a subagent review the diff with fresh context. Many engineers also run skills that hunt for bugs, simplify the diff and check behavior end to end. Boris Cherny estimates that a way to verify its work makes the final result two to three times better.
- **Fix what the reviewer keeps flagging at the source.** Fix it in a skill, with a lint rule, or in an instruction file. `CLAUDE.md` says what the project is and every review loads it, so keep it short in a large codebase and point to other docs. `REVIEW.md`, written by code owners, says what matters in their part of the code; good ones are short, say what failure looks like in that repo, cap nits, list paths to skip, ask for a file and line as evidence, and ask for a summary that starts with a count and says plainly when there is nothing to fix. Check separately that the reviewer follows it, and when a review misses something, ask what the model didn't have in front of it and put the fix in a `CLAUDE.md`, a skill or a new check.
- **Review every PR with an AI reviewer, have other agents verify its findings, and block merge until each finding is answered.** The reviewer reads the diff against the whole repo and the PR's stated intent. Several agents hunt for bugs at once, a separate group votes on each finding, and a finding is posted only if enough agree it is real; findings about only style, diagnostics or cleanup are dropped (filters the team A/B tested on its own PRs). Every finding is fixed or its thread resolved with a reason, security has its own review, and a PR can't merge while a finding from either is open. Lint, type checks, tests and a build also block, and the PR template asks how the change was tested and how to undo it, with the person who asked for the change signing off. Match review depth to risk, and review agents also run nightly over existing code.
- **Scale human approval to risk, and let the change set the tier, not the author.** Low risk (docs, copy, internal-only features, additive changes behind a flag) needs no human once automated review and security checks are green; medium (ordinary product changes, and sensitive areas such as caching, the auto-updater or system prompts) needs one person; high (the highest-risk code plus a small set of paths that always need two people) needs two. A classifier picks the tier from the change, and a second asks whether this change needs another person even if its tier says no. Anything owners list as sensitive, and any CI workflow file, always needs a person. For adoption, the post says to start strict and loosen with evidence.
- **Reserve the lighter approval paths for trusted authors, and never let an agent's approval fill a human slot.** Only authors on the repo's trusted list, mostly the owning team, get the lighter paths; everyone else needs a second person. Automated review can clear a low-risk change but can't fill a slot that calls for a human. An approval covers one specific commit and has to be given again after commits the system can't vouch for, such as an agent's push or a hand-resolved merge. On an agent-written PR, the person directing the agent counts as one of the required reviewers.
- **Keep people on the calls only people can make, and keep one person accountable for every change.** Pulling a senior engineer out of deep work to catch a routine mistake costs far more than an automated review. People stay responsible for whether to build it (direction, taste and scope; one team kept human review for changes from outside the team), risky code such as billing, the auto-updater and CI workflows, architecture that sets a pattern others will copy, and reading the evidence (test output, the command that ran and what it returned, a screenshot, the reviewer's findings). If you can't say what the checks would miss, ask for a real review rather than a quick approval. A person is accountable for every change that ships, whoever typed it.
- **Make mistakes fast to catch and cheap to undo.** The merge queue re-runs every check against main with the change applied, so two PRs that pass separately can't combine into a broken main. New behavior usually ships behind a flag to employees first, public releases go to a `latest` channel before `stable`, flags turn off without a deploy, there is a weekly on-call rotation, and incident reviews ask which layer should have caught the issue. It is a team norm that you usually fix what you land, and the post lists what keeps that from going badly: changes are small, everything is reversible, blast radius sets the bar, regressions surface fast through telemetry and internal use, and it isn't blame (incident reviews look at the system). Noticing a bad merge still depends on the author, on-call and the revert and incident dashboards.
- **Turn incidents into the reviewer's eval, and measure its noise by what people do with its comments.** The team collected past PRs that caused incidents, with their fix-forwards and reverts, had engineers who know the code confirm each bug and where it lived, and runs the reviewer against that set daily, rescoring it whenever its prompts, tools or model change; the set grows with every incident. Each comment is sorted by whether the person fixed it, said it was wrong, said it was intentional or decided it didn't matter, and the reviewer is also run on PRs known to be clean to count reports that would lead to a harmful change. The written priority is real bugs first, review rounds second. Noise costs more when the author is an agent: a person waves off a nit in seconds, while an agent fixes it, adding a commit and another round.
- **Cap review rounds so agent authors and agent reviewers converge.** An agent author and an agent reviewer can keep each other busy indefinitely, and the reviewer was mostly finding a few more old bugs each round. The team now tracks rounds-to-pass alongside recall and changed re-review: after three rounds the reviewer asks the author to step back and reconsider the approach, re-review is diff-only after the first few passes, the reviewer flags the class of bug so the author fixes every instance, and findings already posted aren't repeated. Several rounds can be worthwhile on a risky change, but not on every PR.
- **Let people learn the code from on-demand explainers instead of by reading every diff.** Nobody keeps a complete mental model of the codebase; when someone wants to understand a part of it, they ask Claude to write an explainer for exactly that slice, which takes minutes and reflects the code as it is today. A one-line copy change teaches almost nothing, while an explainer for the module you're about to change teaches a lot. The team has no formal process for this.

## Perishable details
- Product names and commands: Code Review for Claude Code (generally available on Team and Enterprise), `/code-review` for a lighter local run, `/security-review` and the open-source security review GitHub Action; admins set each repo to Quick, Standard or Deep, and findings are tagged Important, Nit or Pre-existing. The product posts findings, not approvals.
- The tiers, classifiers, three-round cap, trusted-author list and `latest`/`stable` channels describe the Claude Code team's own setup as published in October 2026. The post says the line for which low-risk changes merge on automated checks alone "keeps moving".
- Open gap named by the authors: there are no circuit breakers yet that tighten approval when revert and incident numbers move, and engineers there want them before more code moves to zero-human merges.

## Evidence
- From June to September, merged pull requests to Claude Code's codebase more than doubled while the share that had to be reverted fell by more than 40 percent (the outcome of the whole process; the post does not say how much each layer contributed).
- Volume pressure: changes landing per day in Anthropic's monorepo went from about 2,500 in May to more than 30,000 in September, and Claude writes about 90 percent of Claude Code's own code.
- When the AI reviewer's research preview launched, the share of internal PRs getting substantive review comments went from 16% to 54%; most PRs over 1,000 lines get findings and most small ones come back clean.
- One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it. On a git blame of what the reviewer kept flagging, about 59% was code that had been there since the reviewer's first pass. After the convergence changes the post's chart shows fewer review rounds per internal PR (no figure is given in the text).
- Boris Cherny estimates that giving Claude a way to verify its work makes the final result two to three times better (an estimate, not a measurement).
- A typical CLI pull request may run dozens of checks before anyone looks at it.
